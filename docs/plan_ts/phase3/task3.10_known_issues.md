## 使用规范

### Issue 编号规则

`KI-{phase}.{seq}` — 例如 `KI-3.1` 表示在 Phase 3 中发现的第 1 个已知问题。

### Issue 模板

```markdown
## KI-{phase}.{seq}: {一句话标题} {状态 emoji}

| 字段             | 内容                                             |
| ---------------- | ------------------------------------------------ |
| **发现阶段**     | Phase N / Task N.M                               |
| **发现时间**     | YYYY-MM-DD                                       |
| **严重性**       | 🔴 Critical / 🟠 High / 🟡 Medium / 🟢 Low       |
| **类别**         | Logic / Prompt / UX / Performance / Security     |
| **复现路径**     | （请愿内容、触发条件、预期 vs 实际行为）         |
| **根因分析**     | （代码位置 + 问题原因）                          |
| **修复方案**     | （具体修改策略）                                 |
| **影响范围**     | （受影响的文件/模块）                            |
| **状态**         | 🔵 待修复 / 🟡 进行中 / 🟢 已修复 / ⚪ Won't Fix |
| **修复 PR/会话** | （修复时回填）                                   |
```

### 状态 Emoji 速查

| Emoji | 含义                  |
| ----- | --------------------- |
| 🔵    | 待修复 (Open)         |
| 🟡    | 进行中 (In Progress)  |
| 🟢    | 已修复 (Fixed)        |
| ⚪    | Won't Fix / By Design |

### 严重性定义

| 级别        | 定义                               | 修复优先级              |
| ----------- | ---------------------------------- | ----------------------- |
| 🔴 Critical | 阻塞核心流程、数据丢失、安全漏洞   | 立即修复，阻塞当前 Task |
| 🟠 High     | 功能行为明显不合预期，但有变通方案 | 当前 Phase 内修复       |
| 🟡 Medium   | 行为不理想但不影响核心流程         | 下一个 Phase 修复       |
| 🟢 Low      | 代码异味、日志不完善、测试缺失等   | 有空时修复              |

### KI-3.1: 议员达成共识后未能正确短路，死循环消耗 Token 🟢

| 字段             | 内容                                                                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **发现阶段**     | Phase 3 / E2E 联调                                                                                                                                |
| **发现时间**     | 2026-03-25                                                                                                                                        |
| **严重性**       | 🔴 Critical                                                                                                                                       |
| **类别**         | Logic                                                                                                                                             |
| **复现路径**     | 激进派和保守派议员在第 1 轮或 2 轮实际上已输出"辩论已结束"等放弃抵抗文本。但由于只靠 NLP 计分，没有特殊的硬打断状态，系统抛锚未跳出。             |
| **根因分析**     | `debate.ts` 硬退出条件须满足 `roundNum >= min_rounds`。即便打分极低，轮次不够也强行复读激辩。                                                     |
| **修复方案**     | Prompt 中要求议员在达成一致时必须且只能在回答的最开头输出 `[CONSENSUS_REACHED]` 字样。在 `debate.ts` 层级逻辑判定拦截退出，解除强制基础轮数限制。 |
| **影响范围**     | `legislative/debate.ts`, `radical-mp.ts`, `conservative-mp.ts`                                                                                    |
| **状态**         | 🟢 已修复                                                                                                                                         |
| **修复 PR/会话** | (Phase 3 初始联调完毕)                                                                                                                            |

| 字段             | 内容                                                                                                  |
| ---------------- | ----------------------------------------------------------------------------------------------------- |
| **发现阶段**     | Phase 3 / E2E 联调                                                                                    |
| **发现时间**     | 2026-03-25                                                                                            |
| **严重性**       | 🟠 High                                                                                               |
| **类别**         | Logic                                                                                                 |

| **影响范围**     | `server/task-store.ts`                                                                                |
| **状态**         | 🟢 已修复                                                                                             |

| ---------------- | -------------------------------------------------------------------------------------------------- |
| **发现阶段**     | Phase 3 / E2E 联调                                                                                 |
| **发现时间**     | 2026-03-25                                                                                         |
| **严重性**       | 🟠 High                                                                                            |
| **类别**         | Logic                                                                                              |
| **复现路径**     | 抓包检视 SQLite 历史库发现全部深层事件 `payload` 均成空白 `{}`，导致诸如调用的工具等明细不翼而飞。 |

### KI-3.6: 大法官嫌弃 hello world 不是"代码"，判 1.0 偏离度死刑 🟢

| 字段             | 内容                                                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **发现阶段**     | Phase 3 / E2E 联调                                                                                                                                                   |
| **发现时间**     | 2026-03-25                                                                                                                                                           |
| **严重性**       | 🟡 Medium                                                                                                                                                            |
| **类别**         | Prompt                                                                                                                                                               |
| **复现路径**     | 真实 LLM 的的确确生成且抛通了代码，并打印输出。最终依然被大法官拒绝（且是 1.0 极大偏离度）。法官称：“由于我没看到你给我的代码内容，所以用户想要编代码，这不叫代码”。 |
| **根因分析**     | 最初传递时，`sec-engineering.ts` 仅抓取了回溯跑通后的 Terminal StdOut（例如输出了“hello”）。代码源码本体完全散失未向后链输送。                                       |
| **修复方案**     | 返回值硬附串联文本，补充显性头部 `[Generated Python Code]` 将原生代码贴出并跟随 `[Execution Output]`。向法官提交连环双料证据。                                       |
| **影响范围**     | `executive/sec-engineering.ts`                                                                                                                                       |
| **状态**         | 🟢 已修复                                                                                                                                                            |
| **修复 PR/会话** | (Phase 3 初始联调完毕)                                                                                                                                               |

### KI-3.8: 架构加固导致的老测试用例大面积回归 🟢

| 字段             | 内容                                                                                                                                                                                                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **发现阶段**     | Phase 3 / Deep Audit 收尾阶段                                                                                                                                                                                                                                             |
| **发现时间**     | 2026-03-25                                                                                                                                                                                                                                                                            |
| **严重性**       | 🟠 High                                                                                                                                                                                                                                                                             |
| **类别**         | Regression / Tests                                                                                                                                                                                                                                                                        |
| **复现路径**     | 运行 `npm run test`，大量单元测试和深层审计测试报错。如：<br>1. DB 桥接在反序列化验证时预期不匹配<br>2. 任务总线并发报错<br>3. UPSERT 的防呆测试使用了老的 PRIMARY KEY 抛错断言<br>4. 执行端加固前生成的输出后缀缺少匹配断言。 |

| **修复方案**     | 1. `sec-engineering.test.ts`: 更新断言以匹配修正后的空输出格式。<br> 2. `pipeline-bridge.test.ts`: 更新 `extendedPayload` 的深度合并期望模型。<br> 3. `task-store.test.ts`: 替换并重写 UPSERT(覆写) 的冲突行为用例。<br> 4. `phase3-deep-audit2.test.ts` & `phase3-deep-audit8.test.ts`: 修正 mockScorer 返回值签名；将并发隔离测试验证条件从 PRIMARY KEY 改去尝试突破 NOT NULL。       |
| **影响范围**     | 整个后端的单元测试与集成测试防线                                                                                                                                                                         |
