# Task 1.7: 司法分支与双重复核 (Judicial)

> **目标**：实现对执行侧物理沙箱安全的拦截，以及执行产出与法案/用户请愿诉求之间的比对评估护栏。
> **前置依赖**：[Task 1.3](task1.3_base_config.md)
> **对应目录**：`backend/src/agents/judicial/`
> **预估耗时**：1 会话

## 需求说明

1. **`rules-engine.ts` & `kill-switch.ts`**:
   - 防越权的安保人员。遍历法案中的代码内容或执行阶段，匹配 `rm -rf`, `sudo`，高危权限，乃至通过正则表达式寻找文件系统穿透特征词。判断是否属于物理违规。一旦捕获立即返回阻止执行或在审查阶端打回。
2. **`process-reviewer.ts` & `result-reviewer.ts`**:
   - 通过将原需求、执行的控制台日志 `stdout` 以及最终的产出文字推给底层大模型（LLM），要求用严肃语气判定法案是否充分解决了“选民”的要求，给予 0-1 的偏离度打分。如果偏离太远视为服务违宪。
3. **`chief-justice.ts` (首席法官)**:
   - 司法统筹者。统合上面的几种检测报告，汇总为全票通过或一票否决。生成正式的“法庭判决书”（合宪/违宪）。

## 验收维度

- [x] 正则匹配 `kill-switch` 对于包含 `fs.unlink("/")` 或类似高危命令行字眼进行抛错阻拦校验。
- [x] Reviewer 相关组件能将输入字符串合并返回一套有理有据的审阅报告 JSON/字符串，且格式转换处理完备不断层。

## 🛠 开发进展与防线加固总结 (2026-03-22)
**主要更新**：
- **安全检查前置机制修缮**：原 `ChiefJustice` 对恶意指令的熔断判断排在大模型 (`reviewDelivery`) 调用之后。为了避免恶意的 `petition` 请求产生无需有的成本与安全隐患，已全盘梳理逻辑，改为**优先拦截违规危险请求**，验证安全后才可启动深入审判。
- **正则边界防御强化 (Word Boundary)**：引入 `\b` 边界描述符，并更新了 `fs.unlink` 等系统底线的侦测正则组。避免诸如 `charm -rf` 的误触及报错。
- **大模型 JSON 类型防御增强**：增加了针对返回为数字字符串如 `{"score": "0.4"}` 时的解析免疫力，利用强转 `Number()` 并在 `NaN` 层进行兜底。保证了审核评价在偏离度 0.0 ~ 1.0 的安全边界内不出现计算偏移。
- **单测防波堤的搭建**：针对无限执行死循环阀值、越界 Token 数侦察点、伪造恶意参数点生成了全面的单元测试防护验证，最终验证套件 8/8 通过，核心骨架封固。
